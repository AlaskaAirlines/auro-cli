# Post-Mortem: AI Tooling Usage Guide for Docsite Consumption (AB#1592462)

**Scope:** Author a single, authoritative usage guide that explains the Auro CLI's AI-readiness tooling to consumers — how the `auro context`, `auro cem`, and `auro component` commands (plus the docs-site `llms.txt`) fit together to give AI coding assistants an accurate picture of the Auro component API. This work item is documentation only: it ships one file, [`docs/ai-tooling-guide.md`](../ai-tooling-guide.md), and does not add or change any command. It is the capstone of the AI Tooling initiative — the commands themselves landed under separate work items ([AB#1592463](#reference-documents), [AB#1592465](#reference-documents)) and this guide ties them into one coherent workflow for docsite/consumer use.

## What Was Investigated but Deliberately NOT Included

The guide intentionally stays a *usage* document. Several adjacent things were considered and left out to keep it that way:

1. **Command internals / architecture.** How `cem` aggregates and namespaces manifests, how `component` resolves and normalizes names — belongs in the commands' own work items and code, not a consumer guide. The guide describes behavior a reader can observe, not how it is implemented.
2. **Per-component API dumps.** Tempting to inline example output, but that output is generated and would drift. The guide teaches the reader to *run the command* rather than reproducing its output inline.
3. **Assistant-specific setup recipes** (exact "add this rules file" steps for Cursor vs. Copilot vs. Claude). Named the pattern generically ("add it to your project as a rules/context file your assistant reads") rather than couple the doc to any one tool's configuration, which changes frequently.

## What Went Right
- **Framing the whole initiative around one problem.** Leading with the hallucination gap turns four loosely related tools into one story with a clear "why," so a reader understands the *point* before the *mechanics*.
- **The tool-selection table.** The hardest thing for a new reader is knowing which of four things to reach for; a single table answering "what does it give me / when do I use it" does that up front.
- **Examples are runnable and consumer-shaped.** Every code block is a command a docsite reader can paste — including the name-normalization forms (`button` / `auro-button` / `@aurodesignsystem/auro-button`) and the `--json` tool-loop use, which are the two things people get wrong first.
- **Set failure expectations explicitly.** The coverage note pre-empts the most likely support question ("it returned nothing") by stating manifest-less components are skipped by design, not failing.

## What Went Wrong / What the Investigation Missed
- **The guide's accuracy is coupled to sibling commands it doesn't own.** It documents flags (`--output`, `--json`), name normalization, and the aggregate filename (`custom-elements.aggregate.json`) defined in [AB#1592463](#reference-documents)/[AB#1592465](#reference-documents). If those commands change their flags or output, this guide goes stale silently — there is no test binding the doc to the CLI. See recommendations.
- **Work-item boundaries split one feature four ways.** The AI tooling shipped as `context`/`cem` (1592463), `component` (1592465), and this guide (1592462). That made each PR small but means the "one feature" only reads as coherent *here*, in the guide — a reader looking at any single command work item doesn't see the whole.

## Motivation (the "root cause" this addresses)

The AI tooling commands were built across several work items, but there was no single document telling a consumer *why the tooling exists*, *which tool solves which need*, or *how to combine them*. Without that, the commands' value is invisible: `auro context`, `auro cem`, and `auro component` each make sense in isolation but the intended workflow (prime once → look up per-component → optionally index everything) only emerges when they're described together. The gap the guide fills is orientation, not capability.

## Resolution

[`docs/ai-tooling-guide.md`](../ai-tooling-guide.md) — one new file, 141 lines, structured as:

1. **Why these tools exist** — the hallucination/grounding problem in one paragraph.
2. **Intro table** — the four tools (`auro context`, `auro cem`, `auro component <name>`, `llms.txt`) with *what it gives you* and *when to use it*.
3. **Prerequisites** — install via `-g` or `npx`; note that everything reads already-published npm/unpkg data, so no auth/setup beyond a network connection.
4. **Per-tool sections** — `context` (prime once, `--output`), `component <name>` (on-demand lookup, name normalization, `--json` for tool loops), `cem` (full aggregated manifest, package-namespaced paths), and `llms.txt` (automatic web discoverability).
5. **Putting it together** — the end-to-end prime → look-up → index flow.
6. **A note on coverage** — only components publishing a CEM return data; others are skipped gracefully.

The audience is docsite consumers and their AI assistants, so the guide describes observable behavior and runnable commands only — no CLI internals.

- **Markdown/links:** relative links resolve from `docs/post-mortem/` and `docs/`; external links (`llmstxt.org`) are live.

## Outcome
The change is a single non-functional file — [`docs/ai-tooling-guide.md`](../ai-tooling-guide.md). No command code changed. Consumers now have one place that explains the *why*, the *which-tool-when*, and the *how-together* of the Auro AI tooling, aimed squarely at docsite readers and the AI assistants they use. The three commands and `llms.txt` it describes shipped under their own work items; this guide is what makes them read as one feature.

## Recommendations for Future AI-Tooling Docs
1. **Bind the doc to the CLI, or accept drift.** This guide hard-codes flags and an output filename owned by other work items. A lightweight check — e.g. asserting the documented flags exist in `--help` output, or generating the command table from the CLI — would keep the guide honest. Absent that, treat any change to `context`/`cem`/`component` flags as also touching this file.
2. **Keep generated output out of the prose.** The guide deliberately tells readers to *run* the command rather than pasting sample output; hold that line, because CEM/API output changes as components adopt manifests.
3. **Document the workflow, not just the commands.** The highest-value part of this guide is "Putting it together" — the sequence. When adding a new AI tool/command, update that flow, not just the reference table.
4. **State coverage and failure modes up front.** "It returned nothing" is the first support question; answering it in the doc (manifest-less = skipped, coverage grows) prevents it being filed as a bug.

## Latent issues parked (not in scope for AB#1592462)
- **No automated doc-vs-CLI consistency check.** The guide can drift from the commands it documents with no test failing. Parked; see recommendation 1.
- **`llms.txt` lives in the docs site, not this repo.** The guide describes it, but its generation/publishing is owned elsewhere; keeping the guide's description in sync with that file is a manual, cross-repo concern.
