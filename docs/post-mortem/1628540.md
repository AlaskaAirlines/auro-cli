# AB#1628540

## Executive Summary

This work turned the Auro CLI's AI-tooling commands from a first draft into a
dependable "data layer" that AI coding assistants and engineers can rely on.
Three terminal commands — `auro context` (prime an assistant with an accurate
picture of the design system), `auro component <name>` (look up any published
component's API), and `auro cem` (build one machine-readable index of every
component) — now draw from the *real, published* component definitions, prefer
the exact version a project actually has installed, warn when those installs are
behind the latest release, and never hang or crash on the messy edges of
real-world data. The repository also gained its first automated test suite so
this behavior stays correct as the tools evolve.

For product and leadership: an engineer can now, with zero setup, point an AI
assistant at Auro's genuine component API instead of the guesses assistants
otherwise invent — and get answers that match the version they're building
against. This is the foundation the later `auro init` experience will read from.

## The Problem

AI coding assistants have no built-in knowledge of Auro's real component API, so
they invent component names, attributes, and usage that don't exist. The Auro
CLI's job here is to feed assistants Auro's actual, published definitions so they
stop guessing. The first version of that tooling worked in the happy path, but
it had gaps that would erode trust the moment it met real projects:

- It always described the *latest published* component, even when the project on
  the engineer's machine used an older, pinned version — so the guidance could
  silently mismatch the code being written.
- It gave no signal when a project's installed components were behind the latest
  release, so teams had no nudge to update.
- A single stalled network request could make a command hang forever, and a
  single malformed entry in a published manifest could crash a lookup outright.
- The information the assistant-priming document handed out was partly
  hand-written, so it drifted from what the components actually published.

The ticket (PT-M0) framed the goal plainly: make these commands trustworthy
enough to be the *data layer* for the future `auro init` flow, and verify them
end-to-end.

## Root Cause

The gaps traced to a few concrete places in the code:

- **No local resolution.** Manifest fetching went straight to unpkg. There was
  no path that read a package's `custom-elements.json` from the project's own
  `node_modules`, so output could never reflect the installed version.
- **Duplicated fetch logic.** `src/commands/cem.ts` and `src/commands/component.ts`
  each hand-rolled the same unpkg fetch — URL construction plus
  404/non-OK/invalid-JSON branches — so failure handling was inconsistent and
  prone to drift.
- **Unbounded network calls.** The fetch had no timeout. Because `auro cem`
  fires every component's request concurrently through `Promise.all`, one
  connection that unpkg accepted but never answered kept the process alive
  indefinitely.
- **Unguarded rendering of manifest data.** `renderList`/`formatDeclaration` in
  the component formatter assumed every manifest entry had a `name` and every
  field had a `fieldName`. Real manifests violate both (e.g. `auro-formkit@6.0.3`
  ships a nameless `auro-menu` member), producing a crash
  (`Cannot read properties of undefined`) or duplicated rows.
- **Hand-written source of truth.** `src/static/auroContext.ts` baked a
  component table into prose, and `src/commands/agent.ts` kept its own copy of
  the component-package list — which had already drifted (missing `auro-tail`
  and `auro-tokenlist`) — so multiple commands could silently disagree about
  what "the components" even are.

## The Fix

The change set (branch `jbaker/AITooling`, PR #302) addresses each root cause:

- **Shared, local-first manifest resolution** —
  [`src/utils/fetchManifest.ts`](../../src/utils/fetchManifest.ts). A single
  `fetchManifest` helper reads a package's manifest from `node_modules` first
  (honoring `package.json`'s `customElements` path and version), then falls back
  to unpkg; an explicit `--tag`/version always goes to the network. Results carry
  their `source` (`local`/`unpkg`) and resolved version. A `preferLocal` flag
  gates the local read, and an `isInside()` guard confines local reads to
  `node_modules`. `fetchLatestVersion` queries the npm registry for the latest
  published version.
- **Outdated-install flagging** —
  [`src/utils/outdated.ts`](../../src/utils/outdated.ts). `checkOutdated`
  compares installed vs. latest with a real semver comparison (`compareVersions`,
  with prerelease precedence) and reports only when the install is *strictly
  older*, so an ahead-of-latest prerelease is never flagged. `renderOutdatedBanner`
  prints a bordered, aligned banner with a ready-to-run `npm install …@latest`
  command, written to **stderr** so `--json` / document output on stdout stays
  clean. Both `auro context` and `auro component` consume this one helper.
- **Timeout on every fetch** — `AbortSignal.timeout(10s)` bounds each request; a
  timeout surfaces as a *transient* failure, which `auro cem` already reports and
  exits non-zero on.
- **Crash- and dedupe-hardening** —
  [`src/utils/formatComponent.ts`](../../src/utils/formatComponent.ts).
  `renderList` coerces missing labels/descriptions to empty strings,
  `formatDeclaration` filters out nameless members, and attribute-backed fields
  fall back to the attribute `name` when `fieldName` is absent so each field
  renders once.
- **Live, single-sourced data** — `auro context` now builds its component
  reference from live manifests via the shared helper
  ([`src/commands/context.ts`](../../src/commands/context.ts)), falling back to a
  curated table only when too few manifests are available; `auro agent` and the
  other commands now import the one `AURO_COMPONENT_PACKAGES` list from
  [`src/static/auroComponents.ts`](../../src/static/auroComponents.ts).
- **`auro cem` stays canonical** — it passes `preferLocal: false` so the
  aggregated index never mixes per-machine installed versions.
- **First test suite** — a Node `--test` harness with a `.js`→`.ts` resolver hook
  and shared support helpers, covering manifest fetch classification,
  merge/namespacing, outdated logic, formatting, and the three commands
  (`test/*.test.ts`). Pure logic (`mergeManifests`, `partitionOutcomes`) was
  extracted from the commands so it can be tested directly.

## Why This Works

- **Correct version, not just latest.** Local-first resolution means a lookup
  reflects what the project actually imports; the explicit-`--tag` escape hatch
  preserves "give me exactly this version," and unpkg fallback preserves
  zero-install use. The `source`/version carried on each result makes the origin
  visible rather than implicit.
- **No false downgrade advice.** Using real semver comparison and reporting only
  strictly-older installs means the update banner never tells an engineer to
  "upgrade" to an older version (the failure mode a naive string compare would
  cause with prereleases or linked workspaces).
- **Bounded and resilient by construction.** A 10s abort guarantees the process
  can't hang on a stalled connection, and classifying timeouts/5xx as
  *transient* (vs. a genuine 404 = "no CEM yet") lets CI distinguish "incomplete,
  retry" from "correctly skipped." Coercing missing fields and filtering nameless
  members means one bad row degrades gracefully instead of taking down the whole
  lookup.
- **One source of truth resists drift.** Generating the context table from live
  manifests and importing a single package list removes the two places the tools
  could silently disagree — the exact drift that had already dropped `auro-tail`
  and `auro-tokenlist` from the agent command.
- **stderr/stdout discipline.** Advisory output (spinners, banners) goes to
  stderr, so `auro component --json` and `auro context`'s document stay
  machine-parseable — the property that makes them usable inside an assistant's
  tool loop.
- **Tests lock the edges in.** The mixed-schema merge warning and the fetch
  classification can't be exercised by the live command today (every published
  Auro manifest shares one schema version; the network is nondeterministic), so
  unit tests with mocked `fetch` and temp-cwd fixtures are the only way this
  behavior stays correct.

## Outcome

The Auro CLI's AI-tooling commands are now trustworthy against real projects:
they show the version an engineer actually has, flag when it's behind, never hang
on a bad connection, and don't crash on imperfect published data. The
information they hand to AI assistants comes from the components' own published
definitions and a single shared component list, so it stays consistent across
commands. The end-to-end surfaces (`auro context`, `auro component --json`,
`auro cem`, and `llms.txt` discoverability) were verified against a real project,
including offline use and graceful skipping of components that publish no
manifest. The project also has its first automated test coverage, so this
behavior is protected going forward. What remains is the release step: merging
PR #302 and publishing so the improved CLI is installable/`npx`-able.

## Learnings

- **Local-first, network-fallback is the right default for developer tooling.**
  Reflecting the installed version is what makes API guidance match the code an
  engineer is actually writing; the network is the fallback, not the source of
  truth.
- **Distinguish "absent" from "broken."** A 404 (component has no CEM yet) is a
  correct skip; a timeout/5xx is a transient failure that should fail CI. Folding
  them together would either hide real breakage or cry wolf on expected gaps.
- **Every external fetch needs a timeout, especially under `Promise.all`.** One
  unanswered connection among many concurrent requests is enough to wedge the
  whole process.
- **Treat published manifest data as untrusted input.** Real manifests omit
  `name`/`fieldName` and other "required" fields; renderers must coerce and
  filter rather than assume, or a single bad row takes down the command.
- **Compare versions as semver, never as strings.** String inequality misfires on
  prereleases and linked workspaces and can produce downgrade advice; a real
  comparison that reports only strictly-older installs avoids it.
- **One source of truth or it drifts.** The duplicated component list had already
  lost two components; generating from live manifests and importing a single list
  removes the drift surface entirely.
- **Keep advisory output on stderr.** It's what lets `--json` and generated
  documents remain machine-parseable inside an assistant's tool loop.
- **Extract pure logic to make it testable.** Pulling `mergeManifests` and
  `partitionOutcomes` out of the command wiring is what allowed the
  otherwise-unexercisable mixed-schema and fetch-classification behavior to be
  covered by tests.

## Iterations That Didn't Work

- **Hand-written component table baked into the context document.** The original
  `auro context` shipped a static, hand-authored component table (and API
  examples) that drifted from what components actually published — feeding
  assistants stale guidance, the exact problem the tooling exists to prevent. It
  was replaced by generating the reference from live manifests, keeping the
  curated table only as a fallback when too few manifests are available.
- **A second, hand-maintained component list in `auro agent`.** The agent command
  kept its own copy of the package list, which had already drifted out of sync
  (missing `auro-tail` and `auro-tokenlist`), silently excluding those components
  from migration selection. Abandoned in favor of importing the shared
  `AURO_COMPONENT_PACKAGES`.
- **Keying the offline success message off descriptions enriched.** Offline
  `auro context` first decided "found vs. not found" from how many *descriptions*
  it enriched, so an installed manifest that documents no element description
  (e.g. `auro-button@12.3.0`) was wrongly reported as "no manifests found." It was
  changed to key off manifests actually read from `node_modules`, reporting the
  enriched count separately.
- **The `auro init` prototype itself was throwaway.** A `scripts/proto-init.mjs`
  prototype was written only to drive these commands end-to-end and surface
  data-layer gaps; it was never intended to ship, and the composability refactors
  it revealed were deferred to PT-M1 rather than forced into this milestone.
