# AB#1628539

## Executive Summary

This work delivered **Phase 1 of Auro's AI tooling**: making an engineer's AI
assistant "grounded the moment you install." Before this, an assistant asked to
write Auro component markup would invent attributes, slots, and events that don't
exist. After this, the Auro CLI reads the *real* component definitions a project
actually has installed and hands the assistant an accurate picture of the design
system — so it uses the true API instead of guessing.

Concretely, the CLI gained a set of terminal commands (`auro context`,
`auro component`, `auro cem`, and `auro init`) plus editor IntelliSense
generation. Running `auro init` now writes AI grounding files (`AGENTS.md` and a
`CLAUDE.md` that imports it) describing exactly the components installed in the
project, at the version installed, and wires up VS Code autocomplete and hover for
those components. It always describes the installed version (never "latest") and
warns when an installed package is behind its published release. This is a
standalone experience with no dependency on the MCP server or shared catalogs.

## The Problem

AI coding assistants confidently produce Auro markup that looks plausible but is
wrong — attributes that don't exist, events that were never emitted, components
mixed up with each other. There was no zero-setup way for an engineer to point an
assistant at Auro's genuine, version-accurate component API. The result was
hallucinated or broken markup that engineers had to catch and correct by hand, and
that eroded trust in using assistants with the design system at all.

## Root Cause

The design system's authoritative machine-readable definitions (each package's
`custom-elements.json`, the CEM) lived in `node_modules` but nothing translated
them into a form an assistant or editor consumes. The CLI had no command that:
read the *installed* manifests rather than guessing at "latest"; normalised the
various packages (including multi-component monorepo packages like auro-formkit)
into one consistent model; or emitted assistant-facing grounding files and
editor-facing type/IntelliSense artifacts from that model.

## The Fix

Across 82 commits on this branch, the CLI gained an end-to-end grounding pipeline:

- **Tier 1 data layer** (PT-M0, AB#1628540): `auro context`, `auro component`,
  and `auro cem` now build from live, installed manifests, prefer the installed
  version, flag outdated installs, and are hardened against malformed/edge-case
  manifest data. The repo also gained its first automated test suite.
- **Grounding generation** (PT-M1, AB#1628541): `auro init` resolves installed
  components (via `src/init/resolver.ts` normalising CEMs into
  `ResolvedComponent[]`), then renders `AGENTS.md` + an importing `CLAUDE.md` plus
  config. It resolves custom tag names via config, Svelte/AST scan, and prefix
  inference, and prompts to migrate legacy standalone packages to auro-formkit.
- **Monorepo grounding**: multi-component packages resolve all shipped components
  with correct subpath imports and the shared package version.
- **Editor IntelliSense** (PT-M2, AB#1628542): `auro init` emits VS Code
  custom-data, JSX and Svelte type declarations, and CSS `::part()` snippets from
  the CEM, with native DOM events and ARIA/`role`/`data-*` globals; adds
  post-write verification, warning banners, `--reset`, and `--offline`.
- **CEM contract enforcement**: a new `auro cem-check` (static rules + a real
  generation smoke test) turns the previously silent CEM→editor-types hand-off
  into an objective gate, later extended with warn-only richness lints.

## Why This Works

The pipeline is anchored on a single normalisation seam (`resolveComponents`), so
every consumer — grounding files, editor artifacts, and the contract check — reads
the same model derived from the same installed manifests. Because it always grounds
the *installed* version and separately checks for newer releases, guidance never
drifts from what the project actually runs while still surfacing upgrade nudges.
The editor-type builders defensively prune malformed CEM entries so a bad manifest
degrades gracefully rather than crashing — and `cem-check` exists precisely to make
that silent pruning visible to the producing repo, closing the feedback gap that
let thin or broken manifests ship unnoticed.

## Outcome

An engineer can now install Auro packages and, with a single `auro init`, get an
assistant and editor that describe the real components they have — the right
attributes, slots, and events, at the right version. Hallucinated Auro markup drops
because the assistant is reading truth instead of inventing it, and VS Code offers
accurate autocomplete and hover for installed components with no manual setup.

## Learnings

- A single normalisation seam (`resolveComponents` → `ResolvedComponent[]`) is what
  lets grounding, editor types, and the contract check stay consistent; every new
  consumer should read that model, not the raw CEM.
- Grounding the *installed* version (not "latest") is essential for trust — guidance
  must match what the project runs, with upgrade prompts kept as a separate signal.
- Defensive pruning of malformed CEM entries prevents crashes but hides producer
  mistakes; pairing it with an explicit `cem-check` gate is what converts silent
  degradation into an actionable signal.
- The CEM is an untyped, unvalidated hand-off between component repos and the CLI —
  most AI-tooling failures trace back to a CEM that was valid enough to publish but
  too thin or malformed to generate good types.

## Iterations That Didn't Work

- **enumerated-union matching only lowercase `"string"`** — the first cem-check
  richness lint matched a bare lowercase `string` on a curated attribute-name set,
  so auro-accordion's capitalised `"String"` typings slipped through. Broadened to
  an `UNINFORMATIVE_STRING_TYPES` set (`string`/`String`/`any`).
- **`s` (dotAll) regex flag for string-literal detection** — used in the
  union-splitter's literal check but failed `tsc` (TS1501) under the configured
  target; removed the flag since single-line type members never span newlines.
- **Deprecation strikethrough via VS Code HTML custom-data** — that format has no
  deprecation field, so `@deprecated` only flows through to the JSX/Svelte `.d.ts`
  artifacts (grey strikethrough), not VS Code's HTML custom-data path.
