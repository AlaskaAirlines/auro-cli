# AB#1666552

## Executive Summary

Auro now has a check that compares what each change actually does to a component's public interface with the version number its commit messages claim, and reports when the claim is too small. For example, it catches a change labeled as a small fix that removes a public option.

The interface it checks is the component's machine-readable description, which AI tools and other automation use to build pages. So the check treats any change to that description as a real change, even if the component still behaves the same, and new documentation that tools act on counts too.

Before turning the check on, we replayed a year of past releases through it. Commit labels always matched what was released, but in about 4 of every 10 releases the labels understated what the release changed. Half of those came from the documentation cleanup now under way. Based on those results, the team decided to make the check blocking in every component repo right away, with an override label and an emergency bypass for exceptions. Wiring it into pull requests is the next step, in the shared workflow repo.

## Technical Research Document

[Verifying Release Versions Against Code Changes](https://github.com/orgs/AlaskaAirlines/discussions/661). Proposes a check that works out the minimum bump a PR's code changes require and fails PRs whose commits declare less, rolled out in phases. Updated on 2026-10-23 with the Phase 0 results ([comment](https://github.com/AlaskaAirlines/WC-Generator/discussions/661#discussioncomment-19150913)), the "manifest is the contract" rules, and the decision to enforce in every repo right away.

## The Problem

Each Auro release gets its version number only from how engineers label their commits. Nothing checked those labels against what the change did. A change that removes a public option, labeled as a small fix, ships as a patch release, and teams that take patch updates automatically can have their pages break. It also goes the other way: test-only changes trigger needless releases, and real changes labeled as housekeeping don't release until some unrelated release goes out.

The stakes are higher now that AI tools build page content from each component's published description. If that description changes under a small version number, automated tooling can generate different or broken pages with no warning. A version number is a promise to the teams and tools that use Auro, and that promise depended on every engineer labeling every commit correctly.

## Root Cause

- `@semantic-release/commit-analyzer` (configured by `@aurodesignsystem/auro-config/releaserc`) picks the bump only from the commit type, `!`, and `BREAKING CHANGE` footers. commitlint checks that messages are well formed, not that the type matches the change. No tool compared the declared bump with the code.
- The only commit classifier in auro-cli, `auro check-commits`, uses a hand-rolled `RELEASE_COMMIT_TYPES` list instead of the release's own rules, so any check built on it could disagree with the actual release.
- With `conventional-changelog-conventionalcommits` 7, which auro-config 1.3.1 pulls in, commit-analyzer 13 ignores the preset's parser options, so a `feat!:` header without a `BREAKING CHANGE:` footer released nothing. auro-config 1.3.2 fixes this, but each repo releases with whatever its lockfile has. The declared bump therefore depends on the installed versions, not only on the config.
- Phase 0 showed why labels drifted from the code in practice:
  - **JSDoc changes the published contract without changing behavior.** Narrowing a type in JSDoc (`string` → `'sm' | 'md'`), marking inherited properties `@private`, or adding usage tags changes `custom-elements.json` and the TypeScript types generated from it. These went out as `perf:` and `fix:` commits, so as patches. auro-nav 4.1.1 ("unused properties from hyperlink hidden from jsdocs") made 29 properties private and removed 23 attributes in a patch.
  - **The manifest isn't a reliable artifact today.** It isn't reliably committed (auro-button ignores it in `.gitignore`), 17 of 31 packages don't publish it to npm although `package.json` points `customElements` at it, and only auro-button builds under `cem-check --strict` so far.
  - **Generator versions write the manifest differently.** auro-cli and CEM analyzer upgrades changed type formatting, attribute name casing, and which attributes are listed, without any component change.

## The Fix

**Phase 1, PR #350 (merged).** `auro api-diff <baseRef> [headRef]` (`src/commands/api-diff.ts`, backed by `src/scripts/api-diff/`):

- **`index.ts` (`runApiDiff`)** resolves both refs and their merge base, collects classified changes, computes `required` (highest bump) and `declared`, and returns `{ required, reasons, declared, outcome, summary, … }`. It skips the manifest rebuild when only `test/`, `tests/`, `.github/` or `docs/` changed.
- **`git.ts`** builds each ref in a temporary `git worktree` (`npm ci`, `npm run build` by default) and always removes it. Commands run in their own process group, so on SIGINT/SIGTERM `killTree` stops npm along with the shell before the worktree is deleted. `listCommits` skips merge commits and returns commits newest first, as semantic-release expects.
- **`manifest-diff.ts`**, **`package-diff.ts`** and **`bump.ts`** classify manifest, `package.json` and changed-file differences and compare declared vs. required (`fail`/`warn`/`pass`).
- **`declared.ts`** resolves the repo's release config (following `extends`, honoring auro-formkit's copied `.releaserc`) and loads `@semantic-release/commit-analyzer` from the repo's own `node_modules`. It exits 2 if the analyzer isn't installed, so the check reads commits exactly as the release will.
- CLI: `--json`, `--enforce` (exit 1 on `fail`), `--no-rebuild`, `--manifest`, `--install-command`, `--build-command`; exit 2 when the analysis can't run.

**Phase 0 (tooling outside the repo).** Replayed 137 release pairs from 2025-10-01 to 2026-10-23 across the 31 component packages. Each release's manifest was built from its git tag with its own lockfile and cached (`build-manifests.mjs`), then scored with the current rules (`score.mjs`), so rules could be re-scored without rebuilding. Results were posted on the TRD.

**Follow-up branch `jbaker/api-diff-contract-rules-1666552` (commits `5322859`, `a0ac1f0`; PR not yet opened):**

- **Contract rules** in `manifest-diff.ts`: `compareMetadata` classifies `requiredWhen`, `minimum`/`maximum`, `readonly`, `deprecated`, `relevantWhen` and `category`; `compareParameters` compares method parameters by position. A changed default value is major; documenting a default, or removing that documentation, is minor.
- **Normalization fixes** found by Phase 0: attribute names compare case-insensitively; `splitUnion` splits top-level commas and maps `String`/`Number`/`Boolean` to primitives; `normalizeDefault` unwraps braced literals and treats `undefined` as no default; `covers` treats literal → primitive as a widening; nameless entries are ignored.
- **Packaging** in `package-diff.ts`: `isPublishedTarget` decides whether an export's target is in the published package. Adding or removing an export that never resolved is a patch.
- **What ships, with attribution** in `index.ts`/`git.ts`: each ref is built with its own dependencies. When `generatorsDiffer`, `buildManifestAt` builds the base again with the head's auro-cli and analyzer pinned, and each manifest change gets `cause: "code" | "generator"`. Upgrade-caused changes still count; the summary says how many came from the upgrade.
- **Docs and tests:** `docs/versioning-rules.md` lists every rule with examples, linked from the README. Real published manifests from auro-button 12.4.0/12.4.1 and auro-nav 4.1.0/4.1.1 are regression fixtures (`test/fixtures/api-diff/*.min.json`).

**TRD.** Updated with the Phase 0 results, the contract rules, corrected facts (8 repos use different required checks, the manifest isn't reliably committed or published), the decisions below, and a changelog.

## Why This Works

- **The check and the release can't disagree.** The declared bump comes from the same library, config resolution and installed versions the release uses, which avoids the `check-commits` drift and the preset-version trap. Phase 0 confirmed it: commits matched what was released in 67 of 67 comparable releases.
- **It compares what ships.** Each ref is built with its own dependencies, so the comparison is between the manifests tools would actually read. Phase 0 cross-checked this: rebuilt manifests gave the same verdict as the published ones in 43 of 43 pairs.
- **Generator changes are explained, not hidden.** An earlier approach built both sides with the same generator, which would have hidden real contract changes caused by auro-cli upgrades. Attribution keeps them counting and tells reviewers where they came from.
- **One test decides every rule:** would markup that was valid before still be valid, and still work? That keeps decisions consistent (guidance like `relevantWhen` and documented defaults is minor; anything that can invalidate existing markup is major) and makes new cases decidable.
- **Normalization is narrow.** Only differences that can't change what a tool generates are ignored (quote style, union syntax, wrapper names, attribute case). The regression fixtures pin both directions: a formatting-only release stays clean, and a real contract change stays major.
- **Defined failure behavior.** A head that won't build is an error (fail closed); a base that won't build falls back to its committed manifest, then skips the API comparison with a warning (fail open). Interrupted builds don't leave worktrees or npm processes behind.
- **Minimum, not exact match.** Declaring more than required passes, because behavior can break without the manifest changing.

## Outcome

- Auro has a working tool that tells, for any change, which version number it needs, what the commits claim, and why, in plain language. When a tooling upgrade caused part of the difference, it says so.
- A year of past releases showed the gap was real: 26 of 67 comparable releases understated their changes (11 needed a major and shipped as a patch). Most of these were genuine changes to what tools would see, not false alarms.
- The rules are written down for engineers, with examples, and the team's decisions are recorded on the TRD.
- The team decided to make the check blocking in every component repo right away, with an override label for exceptions and the Release Managers' bypass for emergencies. Components still in the documentation cleanup will need to release some of that cleanup as major versions.
- No component or published package has changed yet. Pull-request checks, enforcement, the override label and the release-time safety net come next, in other repos.

## Learnings

- **Treat the published manifest as the API.** When automation builds pages from `custom-elements.json`, JSDoc edits are contract changes. Decide each rule with one test: does markup that was valid before still work after the change?
- **Read the declared bump the way the release does, with the release's own installed versions.** Re-implementing commit-type rules or pinning one analyzer version invites drift, as the `feat!:` preset trap showed.
- **Normalize formatting before classifying.** Before the normalization fixes, the replay flagged about half of all releases; most of that was quote style, union syntax and attribute name case, not real changes.
- **Separate "what changed" from "who caused it."** Hiding generator-caused changes looks like noise reduction but drops real contract changes. Attribute them instead.
- **Cache expensive builds and keep scoring separate.** Rules changed several times during Phase 0; re-scoring cached manifests took seconds instead of hours of rebuilding.
- **Validate a replay against ground truth.** Comparing rebuilt manifests with published ones (43 of 43) is what made the 17 non-publishing packages' results trustworthy.
- **Old release tags may not install with a newer npm.** Lockfiles that lack other platforms' optional dependencies fail `npm ci` under npm 11. CI isn't affected (the base is recent `dev`), but replaying history needs an install fallback.
- **Kill the process group, not just the shell.** With `shell: true`, `child.kill()` signals only `sh`; npm survives and writes into the worktree being deleted. Tests for this must wait until the grandchild is running, or they pass by timing.
- **A historical replay measures the era it covers.** Almost every comparable release predated the `cem-check` standard, so the past can't predict the false-positive rate after the cleanup.
- **Anything shipped in auro-cli reaches every repo immediately** through `npx` at latest. Enforcement stays opt-in (`--enforce`) until the workflow turns it on.

## Iterations That Didn't Work

- **Building both sides with the same generator to compute the required bump (`--same-generator`).** It removed noise from auro-cli upgrades, but under the "manifest is the contract" decision it would have hidden real contract changes those upgrades caused. Replaced with building each side as it ships, plus attribution.
- **Comparing only the manifests published to npm.** Fast and exact for what consumers received, but only 14 of 31 packages publish a manifest, and mostly since late 2025. Replaced with rebuilding from tags, validated against the published manifests.
- **Re-running the full rebuild after each rule change.** Rules changed three times mid-run, and each restart threw away builds. Replaced with a cached build step and a separate, fast scoring step.
- **Plain `npm ci` for old release tags.** It failed under npm 11 on lockfiles missing other platforms' optional dependencies. The replay falls back to `npm install`; the CLI keeps `npm ci` strict, because a loose fallback could pull different dependency versions into the base.
- **The original interrupt test.** It passed without the fix, because the hang command was simple enough for the shell to `exec`, and because it signalled before the install had started. It now uses a compound command and waits until the grandchild is writing.
- **Concluding that generator drift caused most of the noise.** That was true before the normalization fixes. Afterwards, an upgrade alone explained only 1 of 26 under-released releases.
- **Loosening rules to cut the flag rate** (treating `string` → specific values as no change, and letting additions in a fix only warn). Rejected once the manifest was treated as the contract: those flags were real changes tools would see.
